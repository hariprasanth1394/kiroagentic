# JIRA Upload & Linking Guide

## Connection Details

Read from `qe-pipeline/config/pipeline-config.json`:
- **cloudId:** `jira.cloudId`
- **projectKey:** Derived from story key at runtime (e.g., `BREW-94` → `BREW`, `TCOE-146` → `TCOE`)
- **browseUrl:** `jira.storyUrlFormat` (e.g., `https://{cloudId}/browse/{issueKey}`)

**NEVER hardcode project keys or JIRA URLs.** Derive from pipeline-config at runtime.

## Xray Limitation

Xray's native Test Details step editor (action/data/expected result tabs) is NOT accessible via the JIRA MCP API. Steps must be placed in the **description** field in a structured format. The Preconditions tab and Test Sets tab are also not directly settable via API.

**Workaround:** Format description with clear sections that can be manually imported into Xray later, or consumed directly by the Automation Agent from `test-cases.json`.

## Step 1: Deduplicate and Reconcile (create / update / skip)

Before creating anything, fetch what already exists for this story:

```
searchJiraIssuesUsingJql:
  cloudId: {cloudId}
  jql: "issuetype in (Test, 'Test Set') AND labels = '{KEY}' ORDER BY summary ASC"
```

Build a map of existing `{TC-ID → JIRA key}` by parsing the `{TC-ID}` prefix from each summary. Then, for each TC in the freshly generated `test-cases.json`, decide the action — this is what makes a **story re-run** correct (the story changed, tests were regenerated):

| Situation | Action |
|---|---|
| TC-ID not found in JIRA | **CREATE** new Test issue (Steps 2–4) |
| TC-ID found AND generated content differs from the existing issue (steps, preconditions, expected results, priority, or title changed) | **UPDATE** the existing issue in place via `editJiraIssue` — do NOT create a duplicate |
| TC-ID found AND content is identical | **SKIP** (no-op), record as "unchanged" |

### Update path (re-run)

```
editJiraIssue:
  cloudId: {cloudId}
  issueIdOrKey: "{existing Test key for this TC-ID}"
  fields:
    summary: "{TC-ID}: {new title}"
    description: "{regenerated structured description — same format as Step 3}"
    priority: { "name": "{mapped priority}" }
```

Then add a short comment noting the refresh:
```
addCommentToJiraIssue:
  cloudId: {cloudId}
  issueIdOrKey: "{existing Test key}"
  contentFormat: markdown
  commentBody: "🔄 Test updated by QE pipeline re-run of {KEY} on {date} — steps/expected results regenerated from the current story."
```

Re-verify the Test→Story and Test→Test Set links still exist after update (Step 4); re-create any that are missing. Detect "content differs" by comparing the regenerated description/fields against the fetched issue; when in doubt, UPDATE (idempotent) rather than skip, so the JIRA test always reflects the latest story.

## Step 2: Create Test Set

One Test Set per dimension that has test cases:

```
createJiraIssue:
  cloudId: {cloudId}
  projectKey: {derived from story key}
  issueTypeName: Test Set
  summary: "Test Set: {Feature} - {Dimension} ({KEY})"
  contentFormat: markdown
  description: "Automated test set generated by QE Pipeline.\n\nStory: {KEY}\nDimension: {Dimension}\nTest count: {N}"
  additional_fields:
    labels: ["qe-pipeline-generated", "xray-test-set", "{KEY}"]
```

Capture the returned key (e.g., `{PROJECT-KEY}-200`). You'll need it for linking.

---

## Step 3: Create Test Issues

For EACH test case, create a Test issue with structured description:

```
createJiraIssue:
  cloudId: {cloudId}
  projectKey: {derived from story key}
  issueTypeName: Test
  summary: "{TC-ID}: {Title}"
  contentFormat: markdown
  description: |
    **Test Type:** {testType}
    **Dimension:** {dimension}
    **Source Scenario:** {sourceScenarioId}

    ---

    **Preconditions:**
    {preconditions text}

    ---

    **Test Steps:**

    | # | Action | Data | Expected Result |
    |---|---|---|---|
    | 1 | {step.action} {step.target} | {step.value} | {expectedResult for this step} |
    | 2 | {step.action} {step.target} | {step.value} | {expectedResult for this step} |
    | 3 | {step.action} {step.target} | {step.value} | {expectedResult for this step} |
  additional_fields:
    labels: ["automated", "test-{dimension lowercase}", "qe-pipeline-generated", "{KEY}"]
    priority: { "name": "{mapped priority}" }
```

**Priority mapping** (test case priority → JIRA priority name):
- Critical → "Highest"
- High → "High"
- Medium → "Medium"
- Low → "Low"

Capture the returned key (e.g., `{PROJECT-KEY}-201`).

## Step 4: Link IMMEDIATELY After Each Creation

**Link each issue the moment it's created.** Do NOT batch.

After creating each Test issue:

**Link 1 — Test → Story (using the Xray "Test" association):**

Use the link-type name discovered via `getIssueLinkTypes` (cached from Link 2's discovery). Prefer the type whose name is exactly "Test" or contains "Test" / "tests / is tested by"; fall back to "Relates" if none exists.

```
createIssueLink:
  cloudId: {cloudId}
  type: "{exact 'Test' link-type name discovered, else 'Relates'}"
  inwardIssue: "{created Test key}"
  outwardIssue: "{KEY}"
```

The "Test" link type (commonly id 10504, but do NOT hardcode the id — resolve by name from `getIssueLinkTypes`) creates the "tests / is tested by" relationship Xray uses to associate tests with stories. Verify attachment via the re-fetch check described in Link 2.

**Link 2 — Test → Test Set:**

Do NOT assume a link type named "Test Set" exists — in most Jira/Xray instances it does not, and blindly using it is the main reason Test↔Test Set links silently fail. Discover the real types ONCE at the start of the run and cache them:

```
getIssueLinkTypes:
  cloudId: {cloudId}
```

Choose the link type by inspecting the returned names (case-insensitive), in this order:
1. An Xray-specific membership/association type if present (name containing "Test Set", "Tests", or "Association")
2. Otherwise fall back to a generic bidirectional type that exists in the list (e.g., "Relates")

Then create the link using the EXACT name from the discovered list:
```
createIssueLink:
  cloudId: {cloudId}
  type: "{exact link-type name discovered above}"
  inwardIssue: "{Test Set key}"
  outwardIssue: "{created Test key}"
```

> Direction matters: Test Set is the container. Use `inwardIssue = Test Set`, `outwardIssue = Test` so the relationship reads "Test Set → contains → Test" (or "Relates" both ways as fallback).

**Confirm it attached (Item 4 — reproduce to confirm):** after creating the link, immediately re-fetch and verify it is present, because `createIssueLink` can return success while the link does not appear:
```
getJiraIssue:
  cloudId: {cloudId}
  issueIdOrKey: "{created Test key}"
  fields: ["issuelinks"]
```
If the Test Set key is NOT in `issuelinks` → retry ONCE with the fallback "Relates" type, re-verify, and if it still fails log ❌ in the upload summary with the attempted link-type name (so the linking gap is visible and reproducible, not hidden).

**Full sequence per TC (MANDATORY order):**
```
1. createJiraIssue (Test) → get {PROJECT-KEY}-201
2. createIssueLink ({PROJECT-KEY}-201 → {KEY})         ← Test to Story
3. createIssueLink ({PROJECT-KEY}-201 → Test Set key)   ← Test to Test Set
→ ONLY THEN move to next TC
```

---

## Step 5: Link Test Set → Story

After ALL Test issues are created and linked:

```
createIssueLink:
  cloudId: {cloudId}
  type: "Relates"
  inwardIssue: "{Test Set key}"
  outwardIssue: "{KEY}"
```

---

## Step 6: Verify Links

After all creations, verify by fetching the story:

```
getJiraIssue:
  cloudId: {cloudId}
  issueIdOrKey: "{KEY}"
  fields: ["issuelinks"]
```

Check that `issuelinks` contains ALL created keys. Any missing → log as ❌ in upload summary.

---

## Error Handling

| Error | Action |
|---|---|
| `createJiraIssue` fails (400/500) | Log TC ID as failed. Continue with next TC. |
| `createIssueLink` fails | Retry ONCE. If still fails, log ❌. Continue. |
| Rate limited (429) | Wait 5 seconds, retry. |
| Auth failure (401/403) | STOP. Report: "JIRA auth failed." |
| "Test" link type not found | Use `getIssueLinkTypes` to discover. Fall back to "Relates". |

## Upload Summary Format

Write to `jira-upload-summary.md`. Use `jira.storyUrlFormat` from pipeline-config to build clickable links.

> The **Test Set** clickable link(s) below MUST also be echoed back in the chat response after upload (SKILL Step 6), so the user gets the link without opening the file. One line per dimension, e.g. `Test Set (API): {browseUrl}/{Test Set key}`.

```markdown
# JIRA Upload Summary

**Story:** [{KEY}]({browseUrl}/{KEY})
**Date:** {date}
**Project:** {projectKey}

## Test Sets

| Dimension | JIRA Key | Linked to Story |
|---|---|---|
| {Dimension} | [{Test Set key}]({browseUrl}/{Test Set key}) | ✅/❌ |

## Test Cases

Action is one of: `created`, `updated` (re-run refreshed an existing test), `unchanged` (skipped), `failed`.

| TC ID | JIRA Key | Action | Linked to Story | Linked to Test Set |
|---|---|---|---|---|
| TC-API-001 | [{key}]({browseUrl}/{key}) | created | ✅ | ✅ |
| TC-API-002 | [{key}]({browseUrl}/{key}) | updated | ✅ | ✅ |
| TC-API-003 | [{key}]({browseUrl}/{key}) | unchanged | ✅ | ✅ |
| TC-API-004 | — | failed | ❌ creation failed | — |

## Totals

- Created: {N} | Updated: {N} | Unchanged: {N} | Failed: {N}  (of {total})
- Linked to story: {N}/{total}
- Linked to test set: {N}/{total}
- Link failures (❌): {N} — with attempted link-type name for each
```
